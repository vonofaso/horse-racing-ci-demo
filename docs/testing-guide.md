# Тесты и проверки проекта

Нужны Python 3.12 и PostgreSQL. Из корня проекта выполните `make setup`.
Для `make backup` и `make restore` установите клиентские `pg_dump`/`pg_restore`
той же основной версии, что и сервер PostgreSQL.
Версии зависимостей зафиксированы в `requirements.txt` и
`requirements-dev.txt`.

Для интеграционных тестов создайте отдельную базу с именем `*_test` и правом
создавать схемы. Задайте `DATABASE_URL` рабочей базы и `TEST_DATABASE_URL`
тестовой базы. Имена баз должны отличаться. Каждый тест создаёт временную
схему и удаляет её после выполнения; предметные таблицы других схем не
затрагиваются.

Для pytest на компьютере используйте отдельную локальную PostgreSQL,
например с базами `horse_racing` и `horse_racing_test`. Создайте их заранее,
задайте подключения в личном `.env` по шаблону `.env.example`.

Рабочий Compose не создаёт тестовую БД и не публикует PostgreSQL на хост.
Не добавляйте публикацию порта БД ради запуска тестов. Контейнерные сценарии
проверяет отдельная команда `make container-check` через закрытую Docker-сеть.
Порядок запуска рабочего Compose и настройки `.env.compose` — в
[README](../README.md).

```bash
make test-unit         # быстрые проверки без БД
make test-integration  # интеграционные проверки PostgreSQL
make test              # все тесты, покрытие и 36 обязательных мутаций
make mutation          # отдельный прогон обязательных мутаций
make quality           # Ruff, форматирование и Bandit
make verify            # тесты, качество, покрытие и мутации
make container-check   # отдельная приёмка контейнерного окружения
```

Отчёты: `reports/tests.xml` (pytest), `reports/coverage.xml` (покрытие),
`reports/sast.json` (Bandit), `reports/mutations.json` (36 мутаций).
Общий порог покрытия — 40%; все 36 мутаций должны обнаруживаться тестами.
В тестах проверены
авторизация, операции с владельцами, лошадьми, жокеями, состязаниями и
результатами, валидация, обязательные правила результатов, работа с БД и
миграции. По ТЗ это FR-01–FR-03 (учётная запись и сессии) и
FR-05–FR-09 (владельцы, лошади, жокеи, состязания, результаты): 8 из 11
функциональных требований. Интерфейсные сценарии FR-04, FR-10 и FR-11
проверяются вручную при демонстрации. Для защиты можно временно заменить
условие `position: int = Field(gt=0)` на `Field(ge=0)` в `app/schemas.py`, запустить
`make test-unit` и показать падение теста граничного значения. Затем вернуть
условие и повторить проверку.

Правила запрета пропуска тестов и снижения порогов — в
[quality-policy.md](quality-policy.md).

## Контейнерная приёмка ЛР4

`make container-check` проверяет исходники, настройки рабочего Compose и
отдельный одноразовый стенд `tests/container/compose.yaml`: сборку, UID,
лимиты, healthcheck, миграции, отказ БД, SIGTERM, сохранность и backup/restore
в новый volume. Проверочные проекты `hrcheck-*` и `hrrestore-*` изолированы
от рабочих данных. Порты в этом стенде не публикуются.

`make container-policy` — только статическая часть, она не является полной
приёмкой. Runtime-сценарии не запускают итоговый рабочий Compose вместо стенда,
поэтому рабочий запуск и операции БД дополнительно проверяются при интеграции.
Изменение правил приёмки должно проверяться вторым участником;
запреты — в [lab4-container-policy.md](lab4-container-policy.md).

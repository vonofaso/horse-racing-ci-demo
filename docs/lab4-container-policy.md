# Политика контейнерного окружения — ЛР4, задание 13

## Назначение и область действия

Документ устанавливает обязательные эксплуатационные требования к образу
приложения, Dockerfile, Compose-конфигурациям и их переопределениям.
Требования действуют для обоих участников и при проверке изменений в репозитории.
Изменение, нарушающее любой из перечисленных запретов, не принимается.

## 1. Запрет latest и нефиксированных внешних образов

Запрещено использовать `latest`, включая `:latest@sha256:...`, а также ссылаться
на готовый внешний образ без явного тега и SHA256 digest.
Все инструкции `FROM` приложения и готовый образ PostgreSQL в Compose должны
содержать тег и digest. Один тег не закрепляет содержимое внешнего образа.

Приложение, собираемое из проверяемого Dockerfile этого репозитория, получает
явный локальный тег `horse-racing:lab4` либо другой согласованный тег версии,
отличный от `latest`. Для этого локального результата digest заранее не задаётся:
он появляется после сборки. Это правило не разрешает плавающие базовые образы.
Для выпуска рекомендуется сохранять соответствие коммита, тега и image ID/digest.

Прямые и транзитивные Python-зависимости закрепляются в `requirements.lock`
версиями и SHA256; установка выполняется с `--require-hashes --only-binary=:all:`.
Обновление digest, версий или lock-файла оформляется отдельным проверяемым
изменением и проходит `make container-check`.

## 2. Запрет запуска от root

Запрещено запускать приложение и PostgreSQL от системного пользователя root
(UID 0), задавать `USER root`, `user: root`, `user: "0"`, `user: "0:0"` либо
переопределять пользователя через параметры запуска таким образом, чтобы
получить UID 0. Отсутствие `USER` в образе приложения также недопустимо.

В текущей реализации:

- приложение использует `USER 10001:10001` из Dockerfile;
- PostgreSQL использует `user: postgres` в рабочем `compose.yaml`;
- рабочий Compose наследует пользователя приложения из образа.

Запрещены `privileged: true`, host PID namespace и host networking как способы
обхода изоляции. Изменение пользователей и прав volume требует проверки запуска
на новом volume и сохранения работы под непривилегированным UID.

Установка зависимостей и создание пользователя под root на этапе сборки
допустимы: запрет относится к процессам запущенных сервисов.
Linux-пользователь `postgres` не равен роли `postgres` внутри СУБД.
Приложение подключается отдельной ролью БД без прав суперпользователя.

## 3. Запрет помещения секретов в образ и репозиторий

Запрещено помещать пароли, токены, приватные ключи, рабочие строки подключения
с паролями и дампы с данными:

- в Dockerfile, `ENV`, `ARG`, команды `RUN`, исходники или другие слои образа;
- в build context через `COPY`, `ADD` или изменение `.dockerignore`;
- в отслеживаемые Git файлы, примеры конфигурации, отчёты и снимки диагностического вывода.

Удаление файла следующим слоем не устраняет секрет из предыдущего слоя.
Сборочные аргументы не используются для передачи секретов.

В текущей реализации настройки передаются при запуске через окружение.
`.env` и `.env.compose` являются личными файлами, не коммитятся и не копируются
в образ. В Git допускаются `.env.example` и `compose.env.example` только с пустыми
значениями или явными заглушками вместо секретов. `.dockerignore` запрещает весь
контекст по умолчанию и разрешает только необходимые runtime-файлы.

Запрещено возвращать встроенный пароль БД по умолчанию в `app/config.py`.
Не следует публиковать полный вывод `docker compose config`, `docker inspect`
или окружение процесса: runtime-пароли могут присутствовать в этих данных.
Переменные окружения не скрывают секреты от администратора Docker.

## 4. Запрет отключения или ослабления healthcheck

Каждый сервис должен иметь работающую проверку готовности. Запрещены
`HEALTHCHECK NONE`, `healthcheck.disable: true`, `test: ["NONE"]`,
`--no-healthcheck`, удаление проверки и замена её на безусловный успех.
Нельзя ослаблять проверку или её параметры ради получения статуса healthy.

Приложение наследует healthcheck из Dockerfile. Модуль
`scripts/container_health.py` обращается к `/health`, который выполняет
реальный запрос к PostgreSQL. Недоступная БД должна приводить к ошибке пробы.
PostgreSQL проверяется через `pg_isready`; приложение ожидает БД через
`depends_on.db.condition: service_healthy`.

Изменение команды, тайм-аутов, интервалов или числа попыток должно быть
обосновано в описании изменения и проверено при доступной и недоступной БД.
Наличие healthcheck само по себе не гарантирует автоматический перезапуск
контейнера со статусом unhealthy.

## 5. Запрет публикации лишних портов

В текущем рабочем окружении разрешена одна публикация веб-порта приложения:
порт контейнера `8000`, по умолчанию — `127.0.0.1:8000:8000`.
Другой локальный порт хоста задаётся через `APP_PUBLISHED_PORT`, если исходный
порт занят; это не разрешает публикацию дополнительных сервисов.
Привязка к внешнему интерфейсу должна иметь обоснованную необходимость и
быть явно рассмотрена при проверке изменения.

Запрещено:

- публиковать PostgreSQL через `ports`, `-p`, `--publish` или `--publish-all`;
- публиковать отладочные, административные и другие ненужные порты;
- применять host networking для обхода ограничений публикации;
- добавлять обходные публикации в дополнительных Compose-файлах.

Приложение подключается к `db:5432` по внутренней сети `backend`.
Администрирование БД выполняется через `docker compose exec db ...` или
команды проекта. Объявление `EXPOSE 8000` в Dockerfile само по себе порт хоста
не публикует. Проверочный стенд не публикует ни одного порта.

Если будет добавлено дополнительное задание с Nginx, наружу разрешаются
только необходимые порты Nginx `80`/`443`; прямые публикации app и db запрещены.
В текущем рабочем Compose Nginx отсутствует.

## 6. Проверка и принятие изменений

Обязательная команда приёмки контейнерного окружения:

```sh
make container-check
```

Для проверки рабочего `compose.yaml` необходимо предварительно создать личный
`.env.compose` по шаблону `compose.env.example` и задать непустые пароли.
`make container-policy` проверяет только исходники и не заменяет полный прогон.

Текущий `scripts/container_check.py` проверяет Dockerfile, состав разрешённого
контекста сборки, наличие runtime-файлов, настройки разрешённого Compose,
запрет root/отключения healthcheck/лишних портов и фиксацию образов.
В отдельном временном окружении проверяются фактический UID приложения,
параметры собранного образа, готовность, миграции, отказ БД, завершение по SIGTERM,
сохранность данных и восстановление в новый volume.

Рабочий Compose проверяется как конфигурация; runtime-сценарии выполняются
на `tests/container/compose.yaml`. Поэтому они не заменяют проверку запуска
итогового рабочего окружения и просмотр всех применяемых переопределений.
Проверка имён файлов и переменных не является универсальным поиском секретов
в произвольном коде. Отсутствие секретов, смысл healthcheck и необходимость
сетевых публикаций дополнительно проверяет второй участник при review.

При ошибке проверки изменение не принимается. Запрещено удалять проверки,
подавлять их ошибки, подменять актуальный результат старым отчётом или
использовать только статическую проверку вместо полной приёмки.

Связанный порядок задания 14: запуск или обновление рабочего окружения после
изменения контейнерной конфигурации выполняется через `make up` либо
`make container-up`; обе команды требуют успешного `container-check` до `up`.
Makefile задаёт порядок команд, но не ограничивает административный доступ
к Docker CLI. Обход этого порядка прямой командой Docker не допускается.
Эта зависимость не распространяется автоматически на отдельные команды
миграции, резервного копирования и восстановления: их порядок и подтверждение
описаны в документации эксплуатации.

В описании изменения указываются затронутые правила и результаты проверок
итоговой версии. За Dockerfile, приложение и автоматическую приёмку отвечает
первый участник; за рабочий Compose и эксплуатацию БД — второй. Изменения на
стыке частей проверяются обоими участниками.

[запуск, проверка и операции с данными](../README.md).

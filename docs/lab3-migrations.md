# ЛР3: проверка миграций на пустой и заполненной БД

Миграции находятся в `app/migrations/versions/`. Версии применяются строго по
порядку: `001` создаёт владельцев, лошадей, жокеев и состязания; `002` добавляет
результаты и ограничения; `003` добавляет пользователей и сессии; `004` —
призовой фонд состязания с начальным значением 0. Каждая серия
выполняется в транзакции. Повторный запуск не меняет данные. Изменение уже
применённого файла обнаруживается по контрольной сумме.

## Отдельная тестовая база

Создайте PostgreSQL-базу с именем, отличным от рабочей и оканчивающимся на
`_test`, например `horse_racing_test`, и выдайте тестовой роли права на создание схем. Не
используйте рабочую БД: интеграционные тесты создают и удаляют временные схемы.

```bash
export DATABASE_URL='postgresql://horse:YOUR_PASSWORD@127.0.0.1:5432/horse_racing'
export TEST_DATABASE_URL='postgresql://horse:YOUR_PASSWORD@127.0.0.1:5432/horse_racing_test'
make test
```

Тесты `tests/integration/test_migrations.py` создают в тестовой БД временную схему для
каждого сценария и удаляют её после проверки. Они подтверждают:

1. На пустой схеме появляются все четыре версии и нужные таблицы.
2. При переходе с `001` на `004` сохраняются уже записанные владелец и лошадь.
3. Полная прежняя схема v4 с данными принимается; `004` добавляет старым
   состязаниям призовой фонд 0 без потери записей.

## Ручная демонстрация на пустой БД

Укажите в `DATABASE_URL` адрес новой **пустой** демонстрационной БД и выполните:

```bash
make migrate
psql "$DATABASE_URL" -c 'SELECT version, applied_at FROM schema_migrations ORDER BY version;'
make migrate
```

Оба запуска должны завершиться успешно, а запрос после каждого запуска должен
показывать ровно `001`, `002`, `003`, `004`. На заполненной БД до и после `make migrate`
проверьте количество и идентификаторы записей в `owners`, `horses`, `results` и
`users`. Для автоматической проверки заполненной схемы используется
`test_upgrade_preserves_existing_data`.

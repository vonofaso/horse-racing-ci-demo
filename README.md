# Демонстрация защиты CI для лабораторной работы 5

Публичная учебная копия для пунктов 13–16. Проверки выполняются на GitHub-hosted
runners через DinD. Публикация образа в этой копии отключена. Self-hosted runner
и secrets сюда подключать не требуется. Рабочая публикация остаётся в основном
закрытом репозитории. История исходного репозитория в копию не переносилась.

# Скачки

Веб-приложение для учёта лошадей, владельцев, жокеев, состязаний и результатов.
Есть регистрация, вход, cookie-сессии и призовой фонд состязаний.
Интерфейс использует HTTP API приложения.

Технологии: Python 3.12, FastAPI, PostgreSQL, HTML/CSS/JavaScript,
pytest, Ruff и Bandit. Приложение можно запустить в Docker Compose
или локально с отдельной PostgreSQL.

## Быстрый запуск в Docker

Требуются работающий Docker Engine (на macOS/Windows — Docker Desktop),
Docker Compose с поддержкой `up --wait`, Make и Python 3.9+ на компьютере
для управляющих скриптов. Само приложение работает на Python 3.12 в образе.
Для контейнерного запуска устанавливать Python-зависимости приложения
и клиентские утилиты PostgreSQL на компьютер не требуется.
При первой сборке нужен доступ к registry и Python-пакетам.

Из корня проекта:

```bash
cp compose.env.example .env.compose
chmod 600 .env.compose
```

В `.env.compose` заполните **два разных непустых пароля**:

```dotenv
POSTGRES_DB=horse_racing
APP_DB_USER=horse
POSTGRES_PASSWORD=REPLACE_WITH_ADMIN_PASSWORD
APP_DB_PASSWORD=REPLACE_WITH_APP_PASSWORD
APP_IMAGE=horse-racing:lab4
APP_BIND_IP=127.0.0.1
APP_PUBLISHED_PORT=8000
```

Заглушки `REPLACE_WITH_...` замените. Каждый пароль можно сгенерировать командой
`python3 -c 'import secrets; print(secrets.token_hex(24))'`.
Для `APP_DB_PASSWORD` используйте буквы, цифры, `_` и `-`: пароль входит в URL.
Не коммитьте `.env.compose`; он исключён из Git правилом `.env.*`.
Локальный `.env` для запуска без контейнеров — отдельный файл.

Проверьте Docker и запустите окружение:

```bash
docker info
make up
```

`make up` и `make container-up` сначала выполняют полный
`make container-check`. При ошибке проверки рабочие контейнеры не обновляются.
При успехе собирается образ приложения и запускаются `app` и `db`.
PostgreSQL отдельно запускать не нужно; ожидающие миграции выполняются
при старте приложения.

После запуска доступны:

- [Веб-интерфейс](http://127.0.0.1:8000/);
- [Документация API](http://127.0.0.1:8000/docs);
- [Проверка приложения и БД](http://127.0.0.1:8000/health).

Готового аккаунта администратора нет: зарегистрируйте пользователя
в веб-интерфейсе. Пароль должен содержать не менее восьми символов.
Техническая роль PostgreSQL `horse` не является пользователем веб-интерфейса.

## Управление контейнерами

```bash
# Статус и логи рабочего проекта:
docker compose --env-file .env.compose -p horse-racing ps
docker compose --env-file .env.compose -p horse-racing logs -f app

make down                 # удалить контейнеры и сети, сохранив volume БД
make up                   # проверка, сборка и повторный запуск
make container-migrate    # явно применить ожидающие миграции
```

Для выхода из просмотра логов нажмите `Ctrl+C` — приложение продолжит работать.
При изменении исходников или Dockerfile повторите `make up`, чтобы пересобрать
образ. Если порт 8000 занят, задайте `APP_PUBLISHED_PORT=8080` в `.env.compose`
и повторите `make up`; веб-интерфейс будет на `http://127.0.0.1:8080/`.

В рабочем Compose:

- приложение подключается к `db:5432` по внутренней сети `backend`;
- PostgreSQL не публикует порт на компьютере;
- приложение публикует только веб-порт на loopback и подключено также к `frontend`;
- данные хранятся в named volume `horse-racing_pgdata` при стандартном имени проекта;
- приложение работает под UID/GID `10001:10001`, БД — под Linux-пользователем `postgres`;
- приложение наследует healthcheck образа, БД проверяется через `pg_isready`;
- `app` ожидает healthy БД и имеет 20 секунд на остановку, Uvicorn — 15 секунд
  на завершение запросов; для БД задано 30 секунд;
- лимиты app — 256 МиБ и 0.5 CPU, db — 512 МиБ и 1 CPU.
  Это начальные лимиты для учебной нагрузки: они оставляют БД больше памяти,
  ограничивают ресурсы одного экземпляра приложения и требуют пересмотра
  по `docker stats` при росте нагрузки.

SQL-консоль без публикации порта БД:

```bash
docker compose --env-file .env.compose -p horse-racing exec db \
  psql -U horse -d horse_racing
```

Имена роли и БД в этой команде соответствуют шаблону; замените их, если меняли
настройки. SQL-файл `ops/postgres/01-app-user.sql` создаёт отдельную роль
приложения без прав суперпользователя только при инициализации нового volume.
Изменение пароля в `.env.compose` не меняет пароль уже существующей роли БД.

Обычная остановка — `make down`. **`docker compose down -v` удаляет данные БД.**
Не используйте `-v` для штатной остановки или обновления образа.

## Автоматическая приёмка контейнерного окружения

```bash
make container-check
```

Команда проверяет исходники и разрешённую конфигурацию рабочего Compose,
затем создаёт отдельные проекты `hrcheck-*` и `hrrestore-*` с временными volumes:

1. Собирает образ и проверяет UID, ограничения ресурсов, readiness и миграции.
2. Останавливает БД и проверяет отказ readiness приложения.
3. Проверяет корректное завершение приложения по SIGTERM.
4. Проверяет сохранность записи после пересоздания контейнеров и обновления
   на другой image ID.
5. Выполняет backup/restore в новый volume и проверяет восстановленные данные,
   историю миграций и готовность API.
6. Удаляет только созданные проверкой проекты и их временные volumes.

Рабочие данные не очищаются. `tests/container/compose.yaml` используется
для runtime-сценариев приёмки; рабочий `compose.yaml` дополнительно проверяется
как конфигурация. Это разные окружения, поэтому перед защитой следует
проверить запуск и операции с данными также на рабочем Compose.

`make container-policy` выполняет только статическую часть и не заменяет
полный `container-check`. При недоступном Docker или ошибке проверки команда
возвращает ненулевой код. Диагностика показывает этап и stderr с маскированием
реквизитов. После принудительного завершения проверки могут остаться её
временные ресурсы: проверяйте их имена, не используйте глобальный `prune`.

Базовый образ Python и внешний образ PostgreSQL закреплены тегом и digest;
зависимости контейнера — в `requirements.lock` с SHA256. Локальный результат
сборки приложения имеет явный тег `horse-racing:lab4`.

Обязательные запреты задания 13 и порядок принятия изменений:
[политика контейнерного окружения](docs/lab4-container-policy.md).
Nginx и балансировка нескольких экземпляров в текущем проекте не реализованы.

## Резервное копирование и восстановление в Docker

При работающем окружении:

```bash
make container-migrate
make container-backup BACKUP_FILE=backups/lab4-demo.dump
```

`pg_dump` выполняется внутри `db`. Custom-архив сохраняется на компьютере,
проверяется через `pg_restore --list` и не заменяет существующий файл.
`backups/` исключён из Git. Локальные `pg_dump`/`pg_restore` не нужны.

Для восстановления **в новый volume** выберите новое имя проекта и свободный
веб-порт. До операции выполните полную проверку окружения; образ приложения
должен быть уже собран командой `make up`:

```bash
make container-check
RESTORE_PROJECT="horse-restore-$(date +%Y%m%d%H%M%S)"

APP_PUBLISHED_PORT=18086 CONFIRM_RESTORE=YES \
  make container-restore CONTAINER_PROJECT="$RESTORE_PROJECT" \
  BACKUP_FILE=backups/lab4-demo.dump

curl http://127.0.0.1:18086/health

docker compose --env-file .env.compose -p "$RESTORE_PROJECT" exec -T db \
  psql -U horse -d horse_racing -c \
  'SELECT version FROM schema_migrations ORDER BY version;'
```

Проверьте также контрольную запись, созданную до backup. Новое имя проекта
создаёт отдельный volume; основной `horse-racing_pgdata` сохраняется.
`container-restore` заменяет данные **выбранного проекта**, поэтому не задавайте
имя рабочего проекта для демонстрационного восстановления.
При ошибке восстановления транзакция откатывается, приложение выбранного
проекта остаётся остановленным. Успешная операция запускает его и ждёт healthy.

Остановить восстановленное окружение, сохранив его данные:

```bash
make down CONTAINER_PROJECT="$RESTORE_PROJECT"
```

Для проверки сохранности на рабочем окружении создайте запись через интерфейс,
запомните её ID и значения, выполните `make down` и `make up`, проверьте запись
снова. При реальном обновлении приложения сравните также image ID до/после:
одна смена имени тега не доказывает обновление образа.

## Запуск без контейнеров

Нужны Python 3.12, PostgreSQL 14+ и Make. Для локальных backup/restore нужны
клиентские утилиты той же основной версии, что и сервер PostgreSQL.
Python 3.12 указан в `.python-version`.

Установите зависимости:

```bash
make setup
# Если Python доступен под другим именем:
# make setup PYTHON=/путь/к/python3.12
```

Команда создаёт `.venv`, устанавливает `requirements-dev.txt` и выполняет
`pip check`. `make install` — синоним. Прямые зависимости локальной разработки
зафиксированы в `requirements.txt` и `requirements-dev.txt`.

Запустите локальную PostgreSQL. В административной SQL-консоли создайте роль
и базу; пароль задайте интерактивно:

```sql
CREATE ROLE horse WITH LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password horse
CREATE DATABASE horse_racing OWNER horse;
```

Скопируйте `.env.example` в `.env`, задайте реальный `DATABASE_URL` и выполните:

```bash
cp .env.example .env
# Отредактируйте .env перед запуском:
make run
```

`make` читает `.env` автоматически. Для прямого запуска:

```bash
set -a
source .env
set +a
.venv/bin/python -m app
```

`DATABASE_URL` обязателен; встроенного пароля и адреса БД по умолчанию нет.
Специальные символы в пароле необходимо кодировать в URL, например `@` как `%40`.
Миграции применяются при старте; остановка локального приложения — `Ctrl+C`.
Инструкции развёртывания на VM из ЛР2 остаются в
[docs/lab2-repeatable-deployment.md](docs/lab2-repeatable-deployment.md).

## Настройки приложения

| Переменная | Назначение | Локальное значение по умолчанию |
|---|---|---|
| `APP_NAME` | название приложения | `Скачки API` |
| `APP_VERSION` | версия | `v0.1.0` |
| `APP_HOST` | адрес прослушивания | `127.0.0.1` |
| `APP_PORT` | порт внутри процесса | `8000` |
| `APP_RELOAD` | перезагрузка при изменениях | `false` |
| `LOG_LEVEL` | уровень логов | `info` |
| `DATABASE_URL` | подключение к PostgreSQL | не задано, требуется при запуске |

Образ задаёт `APP_HOST=0.0.0.0`, чтобы принимать запросы внутри контейнера;
публикация порта хоста настраивается отдельно. `APP_PUBLISHED_PORT` меняет порт
хоста, а не `APP_PORT` процесса.

Переменные Make для контейнерных операций:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CONTAINER_COMPOSE` | `compose.yaml` | рабочая конфигурация |
| `CONTAINER_ENV_FILE` | `.env.compose` | личные настройки Compose |
| `CONTAINER_PROJECT` | `horse-racing` | проект и пространство имён volumes |
| `BACKUP_FILE` | файл в `backups/` с временной меткой | путь backup/restore |
| `CONFIRM_RESTORE` | не задано | для восстановления требуется `YES` |

## API и правила приложения

Публичные маршруты: `POST /auth/register`, `POST /auth/login`,
`POST /auth/logout`, `GET /auth/me`. Для `/owners`, `/horses`, `/jockeys`,
`/competitions`, `/results` поддерживаются создание, чтение, изменение и удаление.
Предметные данные требуют действующей сессии.

Основные ограничения:

- ссылки на владельцев, лошадей, жокеев и состязания должны существовать;
- одна лошадь и один жокей не могут иметь два результата в одном состязании;
- место недисквалифицированного участника уникально в состязании;
- даты рождения не находятся в будущем, вес, время и дистанция положительны;
- призовой фонд в рублях неотрицателен;
- связанные записи нельзя удалить, пока они используются;
- пароли хранятся как PBKDF2-SHA256-хеши с солью;
- сессия передаётся cookie с `HttpOnly` и `SameSite=Lax`.

Подробности: [API](docs/api.md), [схема данных](docs/data-schema.md).

## Тесты и контроль качества

```bash
make setup
make test-unit         # без БД
make test-integration  # настоящая отдельная PostgreSQL
make quality           # Ruff, форматирование и Bandit
make verify            # quality, тесты, покрытие и 36 обязательных мутаций
make container-check   # отдельная приёмка контейнерного окружения
```

Для интеграционных тестов задайте `DATABASE_URL` и `TEST_DATABASE_URL`.
Тестовая БД должна существовать, отличаться от рабочей и иметь суффикс `_test`;
роль должна иметь право создавать схемы. Каждый тест создаёт и удаляет свою
временную схему. Не указывайте рабочую БД как тестовую.

`make verify` и `make container-check` проверяют разные свойства и не заменяют
друг друга. Рабочий Compose не создаёт тестовую БД и не публикует PostgreSQL;
для запуска pytest на компьютере используйте отдельную локальную тестовую БД.
Порог покрытия — 40%; обязательные мутации — 36/36. Отчёты `reports/` не коммитятся.
Подробности: [проверки](docs/testing-guide.md),
[политика качества](docs/quality-policy.md),
[внесение изменений](docs/contributing.md).

Работа с GitHub Actions, запуск проверок в DinD и сценарии защиты описаны
в [руководстве по ЛР5](docs/lab5-ci.md).

## Миграции и локальные операции с БД

Миграции `001`–`004` создают справочники, результаты, пользователей/сессии
и призовой фонд. История и контрольные суммы — в `schema_migrations`.
Повторный запуск не меняет применённые миграции, изменение их файлов
обнаруживается по контрольной сумме. Мигратор использует блокировку PostgreSQL.

Для режима без контейнеров:

```bash
make migrate
make backup BACKUP_FILE=backups/before-change.dump

RESTORE_DATABASE_URL='postgresql://horse:YOUR_PASSWORD@127.0.0.1:5432/horse_restore' \
  CONFIRM_RESTORE=YES make restore BACKUP_FILE=backups/before-change.dump
```

Для локального restore целевая база должна существовать.
`YOUR_PASSWORD` — заглушка. Не путайте эти команды с `container-*`, которые
используют подключение и утилиты внутри выбранного Compose-проекта.
Описание миграций: [docs/lab3-migrations.md](docs/lab3-migrations.md).

Изменения основной ветки принимаются через Pull Request после успешного CI и проверки вторым участником.
